# Code style

This document lists the code conventions used in Shiftly. Each rule comes from the existing code, its configs, or the other docs. Where a rule is planned and not yet in the code, the section says so.

The codebase does not yet follow these rules everywhere. Files generated by shadcn/ui and some template files differ. When you edit a file, match that file's style. Do not reformat existing code only to match this guide. Architecture is in [ARCHITECTURE.md](ARCHITECTURE.md), and test strategy is in [TESTING.md](TESTING.md).

## Tooling

| Tool | Config | How to run | Enforced |
| --- | --- | --- | --- |
| Package manager | `bun.lock` | `bun install`, `bunx <tool>` | Use Bun. Do not use npm |
| TypeScript, `strict: true` | `tsconfig.json` | `bunx tsc --noEmit` | Run manually. See [TESTING.md](TESTING.md#current-status) for current failures |
| ESLint, Next.js Core Web Vitals and TypeScript rules | `eslint.config.mjs` | `bun run lint` | Run manually. See [TESTING.md](TESTING.md#current-status) for current failures |
| Formatter | None | None | No Prettier or EditorConfig. Follow the rules below by hand |

## Formatting

- Indent with two spaces. The repo has no tabs.
- Use double quotes for strings and imports. No file uses single quotes.
- Use semicolons in hand-written code, such as `app/`, `lib/`, `database/`, and the config files. Files generated by shadcn/ui in `components/ui/` and most of `components/dashboard/` have no semicolons. Keep their style.
- Add trailing commas in multi-line objects, arrays, and arguments. See `database/schema/auth-schema.ts`.
- Wrap long call chains and argument lists across lines, as in `database/schema/auth-schema.ts`.

## Imports

- Use the `@/` alias for imports across folders in `app/`, `components/`, and `hooks/`. The alias maps to the project root (`tsconfig.json`).
- Use relative paths only for files in the same folder. The auth route and `lib/auth.ts` use relative paths today. Do not copy that into new code.
- Import `cn` from `"cn"`, as [CLAUDE.md](../CLAUDE.md) states. `lib/utils.ts` re-exports it, and one file imports from `@/lib/utils`. Both work.
- No lint rule enforces import order. In new files, group imports by source: packages first, then `@/` aliases, then relative paths.

## Naming

| Item | Convention | Example |
| --- | --- | --- |
| Files | kebab-case | `use-mobile.ts`, `app-sidebar.tsx`, `auth-client.ts` |
| Next.js route files | Reserved names | `page.tsx`, `layout.tsx`, `loading.tsx`, `route.ts` |
| Components | PascalCase | `NavUser`, `Header` |
| Hooks | `use` prefix, camelCase | `useIsMobile` |
| Constants | UPPER_SNAKE_CASE | `MOBILE_BREAKPOINT` |
| Variables and functions | camelCase | `setIsMobile` |
| Database tables | Singular, lowercase, in the `pgTable` name | `user`, `session`, `account` |
| Database columns | `snake_case` in SQL, `camelCase` in TypeScript | `email_verified` as `emailVerified` |
| Relations | `<table>Relations` | `userRelations` |
| Indexes | `<table>_<column>_idx`, with the column in the TypeScript name | `session_userId_idx` on `userId` |
| Domain terms | Use the names from [CLAUDE.md](../CLAUDE.md) | Use "department", not "Work Area" |

Migration files in `database/migration/` are generated by drizzle-kit. Do not rename them.

## Exports

- Next.js pages, layouts, and `loading.tsx` files use a default export: `export default function Page()`.
- Other components and hooks use a named export: `export function NavUser()`. The exception is `components/home/`, where components use default exports. Match the folder or file you are editing.
- Modules that export objects or functions, such as `lib/auth.ts`, use `export const`.
- Type a small props object inline, as in `app/dashboard/layout.tsx`: `{ children }: { children: React.ReactNode }`.

## Components and UI

- Primitives in `components/ui/` are generated by shadcn/ui (`components.json`, style `base-nova`, icons from lucide). To change a variant, edit the primitive. Do not restyle the same thing in each page. See [CLAUDE.md](../CLAUDE.md).
- Add `"use client"` only to a file that uses state, effects, or event handlers. Most `components/ui/` files and several `components/dashboard/` files already have it.
- Style with Tailwind classes that use the theme tokens, such as `bg-primary` or `text-muted-foreground`. Do not write hex colors or arbitrary color values in components. The tokens are defined in `app/globals.css`. See [DESIGN.md](DESIGN.md).
- Use the Tailwind spacing scale. [DESIGN.md](DESIGN.md) sets spacing in multiples of 8 px.
- The app is light mode only. Do not add dark-mode styles.

## Comments

- Hand-written code has few comments. Add one only when the reason for the code is not clear from the code itself.
- Do not write comments that restate the code.
- Leave the comments in generated files as they are.

## Next.js

- Read the relevant guide in `node_modules/next/dist/docs/` before you write Next.js code. This version has breaking changes, so APIs and file conventions may differ from older Next.js versions.
- In Next.js 16, use `proxy.ts` instead of `middleware.ts`.
- `cacheComponents` is enabled in `next.config.ts`. Check the Next.js docs before you add dynamic data to a route.

## Database and schema

- `database/schema/*.ts` is the source of truth. `drizzle.config.ts` reads every file in that folder, so a new table goes in a new file there.
- Generate migrations with `bunx drizzle-kit generate`, then apply them with `bunx drizzle-kit migrate`. Do not use `push` on a shared database, because it changes the database without creating migration files.
- Do not edit files in `database/migration/` by hand.
- Never commit `.env`. Environment variables are listed in [ARCHITECTURE.md](ARCHITECTURE.md#configuration).

## Tests

- Name test files `*.test.ts`. The folder layout is not decided yet. See [TESTING.md](TESTING.md#open-decisions).
- Name each test after the rule and the case, for example `rejects shift change from 3 to 2 before 7 working days`.
- Test one behavior per test. Write separate tests for valid and invalid input.

## Roster engine (planned)

- Put the engine in plain TypeScript under `lib/roster/`. It must not import from Next.js or the database. See [ARCHITECTURE.md](ARCHITECTURE.md#folder-layout).
- The engine is deterministic: the same input always gives the same roster. Do not read the clock or generate random values inside the engine. Pass dates and any other varying input in as arguments.
- The engine does not use an AI model.
- A rule that cannot be met must be recorded as a conflict with its reason. Never skip a rule silently.

## Commits

- Use Conventional Commits: `type(scope): summary`, with the summary in the imperative mood. The history uses types such as `docs`, `feat`, and `build`.

## Open decisions

- **Formatter.** None is configured. Adding Prettier would settle the semicolon and quote differences above, but it would reformat existing files.
- **Import order.** No rule enforces it.
- **Component export style.** `components/home/` uses default exports and `components/dashboard/` uses named exports. Pick one for new components.
- **Test folder layout.** Not chosen. See [TESTING.md](TESTING.md#open-decisions).
